# 멘티 프로젝트 플레이북

이 문서는 멘티가 프로젝트에서 다룰 질문·작업·완료 기준을 안내한다. Codex와 Claude Code도 이 문서를 읽고, 멘티가 다음 작업을 정하지 못할 때 **할 수 있는 일을 제안하며 함께 진행**한다. 역할은 우선순위이지 작업 허가 목록이 아니다. 학생의 질문·가설·선호를 존중하고, 이유를 설명할 기회를 남긴다. 일반적인 Git·환경 설정·반복 코딩은 에이전트가 대신 처리한다.

## 먼저 확인할 사실

- 협업 저장소 `PublicData_AI_Agent`에는 현재 앱 코드가 없고 설계·멘티 지침이 있다. 데모 코드는 별도 [daegu_lifecycle_agent](https://github.com/donggwonY/daegu_lifecycle_agent)에 있다. 접근 가능한 데모 체크아웃이 없으면 읽기 전용으로 확인할 수 있지만, 코드 이동이나 운영 DB 변경은 결정된 것처럼 가정하지 않는다.
- 참고 구현 저장소에서는 `pipeline/build.py`, `pipeline/external.py`의 배치 계산 → `data/processed/*.parquet` → `core/tools.py`의 조회·계산 함수 → Streamlit 상담 또는 MCP 연결로 이어진다. 주소/자리 이력 조회, Kaplan–Meier 생존곡선, 상권 단계, 업종 전이 등의 **통계·규칙 기반 분석이 이미 존재**한다. LLM이 모든 숫자를 계산하는 구조는 아니다. 현재 확인한 코드에는 학습·평가된 예측 모델이 없다. 함수 목록과 개수는 작업 시점의 `core/tools.py`에서 다시 확인한다.
- 데모의 `meta.json`과 Parquet는 한 시점의 스냅샷이다. 예를 들어 확인 당시 `reference_date`는 2026-09-08이었으나 새 체크아웃에서는 반드시 다시 읽는다. 원본 인허가 CSV와 일부 보조 CSV는 로컬에 없을 수 있다. 없는 원본으로 배치를 성공한 척하거나 공개 출처와 이용 조건을 확인하지 않은 데이터를 새로 합치지 않는다.
- 목표는 `LLM + MCP` 자체가 아니라 **재현 가능한 데이터 분석 → 필요할 때 검증된 통계/ML 결과 → 근거를 설명하는 상담**이다. Supabase 이전은 향후 작업이며, 분석 실험은 우선 현재 Parquet에서도 할 수 있다.

## 코딩 에이전트가 멘티와 매 세션 하는 일

1. 개발 세션을 시작할 때 `pull` 스킬로 원격 `main`을 확인하고, 이어서 `.mentee/profile.json`의 이름·트랙·첫 작업 ID, [작업판](WORKBOARD.md), 관련 산출물, Git 상태를 읽는다. 로컬 변경 때문에 fast-forward가 막히면 변경을 보존하고 상태를 먼저 해결한다. 프로필이 없으면 `mentee-init`을 안내한다. 기록이 실제 파일과 다르면 파일·테스트 결과를 우선하고 작업판을 정정한다.
2. 학생이 구체적 작업을 요청했다면 그 일을 돕는다. 요청이 모호하거나 "뭘 해야 하죠?"라면 작업판에서 **현재 가능한 작은 작업 하나를 추천**하고, 관심에 맞는 대안 1~2개를 제시한다. 무엇을 확인할지, 왜 지금 필요한지, 완료 증거가 무엇인지 한 화면 안에 설명한다. 막연히 "무엇을 하고 싶나요?"라고만 묻지 않는다.
3. 추천 전 의존성과 범위를 확인한다. 실제 데이터·코드가 없으면 가능한 탐색/설계 과제로 바꾸고, 필요한 입력을 명시한다. 약 1회 작업에서 확인할 수 있는 산출물로 쪼개며 다른 학생의 결과를 기다리는 동안 할 수 있는 독립 작업을 찾는다.
4. 분석 문제에서는 처음부터 정답 모델·변수·결론을 주지 않는다. 먼저 **질문 → 관측 단위 → 기준 시점 → 결과 정의 → 데이터 가용성**을 학생이 말하게 돕는다. 막히면 작은 예시와 두 선택지로 좁힌다. 학생이 구현 도움을 원하면 함께 코드와 실험을 만들되 왜 그런 설계를 택했는지 확인한다.
5. 각 작업이 끝나면 산출물 위치, 재현 명령, 관찰 결과, 한계, 다음 질문을 [작업판](WORKBOARD.md)에 남긴다. 완료 여부는 파일·테스트·표·그림 등 근거로 판단한다. 단순히 스크립트를 실행했다는 이유로 분석을 완료 처리하지 않는다.
6. 학생이 원격 반영을 요청하면 `commit-push` 스킬을 사용한다. 에이전트가 대신 Git을 처리하되, 실험이 미완성이라면 진행 상태와 한계를 커밋 메시지·문서에 분명히 남긴다.

### 설명의 깊이 조절

처음에는 학생의 가설과 예상 결과를 한두 문장으로 듣고 **힌트 → 예시 → 공동 구현** 순서로 돕는다. 학생이 이미 이해한 부분은 건너뛴다. 디버깅·환경 문제는 에이전트가 적극 해결해 분석 시간을 지킨다. 부정확한 결론은 친절하게 반박하고 원자료/계산으로 확인한다. 발표를 위해 예쁜 그래프만 먼저 만들거나, 모델 사용 자체를 성과로 취급하지 않는다.

## 공통 분석 계약

모든 통계·ML 실험은 아래 항목을 짧은 Markdown 실험 기록과 재현 가능한 코드/노트북에 남긴다. 처음부터 완벽한 보고서를 요구하지 않고 작업별로 채워 간다.

| 항목 | 학생에게 확인할 질문 |
| --- | --- |
| 의사결정 질문 | 사용자가 무엇을 판단할 때 이 결과가 필요한가? 기존 도구 결과보다 무엇이 더 나은가? |
| 관측 단위·시점 | 한 행이 점포·자리·행정동·월 중 무엇인가? 예측 시점에 실제 알 수 있는 변수인가? |
| 결과·제외 기준 | 폐업 신고/영업 상태/재입점 등 무엇을 사건으로 볼 것인가? 관측 중인 점포, 누락 날짜, 주소 불명은 어떻게 처리할까? |
| 출처·품질 | 각 열의 출처, 기준일, 조인 키, 결측·중복·좌표 오류, 표본 수는? 소스 간 지역·시점 정의가 같은가? |
| 기준선 | 규칙/전 기간 평균/최근 값/기존 Kaplan–Meier 등 간단한 방법은 얼마만큼 맞히는가? |
| 평가 | 미래 시점을 남겨둔 검증인가? 같은 자리·상권의 반복 관측이 학습과 평가에 섞이지 않았는가? 지표와 불확실성은? |
| 결과 해석 | 어느 지역·업종·기간에서 틀리는가? 작은 표본에서 왜 확신할 수 없는가? 예측과 인과 주장을 구분했는가? |
| 채택 결정 | 기준선 대비 이득·유지 비용·오류 위험을 설명할 수 있는가? 못한다면 분석 결과로 남길 것인가? |

시간이 있는 자료를 무작위 행 분할만으로 평가하지 않는다. 시간 순서의 학습/검증/최종 테스트 기간을 분리하고, 동일 자리·인접 지역 반복 관측의 누출도 점검한다. 확률을 보여주려면 보정 상태와 표본 수를 확인한다. 데이터 기준일 이후의 정보로 과거 예측을 만들지 않는다. 인허가상 폐업은 사업 실패의 완전한 측정이 아니고, 신규 인허가 부재는 실제 임대 공실의 직접 관측이 아니다. 모델이 약하거나 편향되면 서비스에 넣지 않는 판단도 좋은 결과다.

## 염동권: 엔지니어링 중심 트랙

염동권은 화면만 만드는 담당이 아니다. **데이터가 갱신되어도 같은 숫자를 안정적으로 제공하는 시스템**을 책임지고, 세은·선경의 분석 결과를 사용자 경험으로 연결한다.

### E-01 현재 구조를 재현 가능한 설계로 만들기

- 시작점: 데모의 `app.py`, `core/tools.py`, `pipeline/`, `requirements*.txt`, 배포 설정을 읽는다. 실제 앱 코드가 이 저장소에 없는 사실을 먼저 확인한다.
- 질문: 배치는 어디서 실행되고, 실패하면 이전 스냅샷은 남는가? Streamlit 서버가 시작할 때 무엇을 로드하는가? 키와 데이터 버전은 어디서 관리하는가? 코드 이전이 필요한가, 두 저장소를 연결하면 되는가?
- 산출물: 실행/배포 흐름도, 로컬 재현 절차, 의존성·비밀값 목록, 이전 여부에 대한 선택지와 판단 근거. 문서의 명령은 직접 시험하거나 미검증이라고 표시한다.

### E-02 데이터 계약과 저장소 계층

- 세은의 데이터 사전을 받아 Parquet 테이블별 키·자료형·기준일·조회 패턴을 정리한다. Supabase로 옮길 때 단순 업로드보다 행 수·고유 키·대표 지표·조회 결과의 전후 일치를 확인하는 방법을 먼저 설계한다.
- 읽기 전용 조회, 인덱스, 비밀키 서버 측 보관, 배치 실패 시 이전 정상 버전 유지, 로컬 Parquet 대체 경로를 고려한다.
- 산출물: 작은 조회 인터페이스나 이행 실험, 일치 검증 기록, 되돌리는 방법. 실제 운영 DB나 배포 변경은 관리자 결정 후 진행한다.

### E-03 통계·ML 결과를 서비스에 안전하게 연결

- 세은·선경의 **검증된** 결과를 받아 `기준일/모델 버전/표본 수/정의/불확실성/적용 가능 범위`가 같이 이동하는 결과 형식을 설계한다.
- 학습은 오프라인 배치에서, Streamlit 요청은 저장된 결과를 읽는 쪽으로 시작한다. 모델이 없거나 오래되었거나 입력이 범위 밖이면 기존 기술통계 도구로 되돌리는 동작을 정한다.
- 산출물: 하나의 결과 조회 경로와 UI 시연. LLM이 모델을 임의로 재학습하거나 근거 없는 확률을 생성하지 못하게 한다.

### E-04 발표 가능한 운영 품질

- 대표 질문의 응답/도구 결과 일치, Streamlit 재시작, 데이터 갱신 실패, Gemini 한도/지연, 작은 화면, 접근성, 오류 안내를 점검한다.
- 산출물: 핵심 경로 자동 검사, 장애 시 사용자 안내, 배포 체크리스트와 재현 가능한 데모. 복잡한 서버 분리는 현재 필요가 입증될 때만 제안한다.

함께 살펴볼 질문 예: "세은이 데이터 정의를 바꾸면 어느 테스트가 먼저 실패해야 할까?", "선경의 모델 결과가 없을 때 화면은 무엇을 보여줘야 할까?" 구현 선택은 학생이 근거를 대면 바꿀 수 있다.

## 김세은: 데이터 품질·생존/결과 모델링 트랙

김세은은 **데이터 정의와 결과 변수의 신뢰도**를 주도한다. 분석용 테이블을 많이 다루되, 검증용 미래 기간은 남기고, 출처가 불명확한 데이터를 무작정 늘리지 않는다.

### D-01 데이터 지형도와 데이터 사전

- `stores`, `units`, `transitions`, `area_year`, `area_cycle`, `survival`, `vacancy_area`와 보조 `poi`, `area_context`, `legal_admin_map`, `station_traffic`, `parking`, `market`를 조사한다. 처음에는 전부 모델에 넣지 말고 행 수·컬럼·키·결측·중복·최신 기준일·생성 코드·조인 관계를 표로 만든다.
- 원본 CSV가 있으면 CP949 인코딩과 인허가 3종의 컬럼 차이를 확인한다. 없으면 Parquet/`meta.json`에서 알 수 있는 것과 알 수 없는 것을 구분한다.
- 산출물: 데이터 사전과 품질 요약을 다시 만들 수 있는 스크립트/노트북. 이상한 수치 3건 이상을 표본 행과 함께 조사한다.

### D-02 분석 정의 감사와 탐색 분석

- 주소 정규화·자리(unit) 정의, 업종 별칭, 폐업/영업중 상태, 90일~3년 공실 후보, 2010년 이후 생존 코호트, 60일 양도양수 허용, 행정동 매핑을 작은 표본으로 검증한다.
- 구·동·업종·개업연도별 개업/폐업·표본 크기·누락률을 비교하고, 관측 기간 차이와 작은 집단을 표시한다. 기존 `meta.json` 지표를 재현하거나 차이를 기록한다.
- 산출물: 정의별 민감도 표와 "이 결과를 사용하면 안 되는 경우" 목록. 선경의 보조 데이터 결합 기준에 필요한 키와 기준일을 전달한다.

### D-03 생존분석에서 예측 문제로 확장

- 먼저 기존 Kaplan–Meier 결과를 재현하고 관측 중인 점포의 중도절단, 관측 시작·종료, 업종별 표본 수를 설명한다. 이후 **학생이 선택한** 질문(예: 특정 기간의 폐업 신고 위험)에 대해 관측 단위·예측 시점·특징·사건을 정한다.
- 전 기간 평균/KM 같은 기준선과 로지스틱 회귀, Cox 모형, 트리 기반 모형 중 문제에 맞는 후보를 비교한다. 12개월 결과를 택한다면 추적 기간이 충분하지 않은 행을 어떻게 다룰지 먼저 결정한다.
- 과거 시점에 알 수 없던 폐업일·미래 상권 집계·전체 기간으로 계산한 특징을 입력에서 제외한다. 시간 분리와 자리/상권 단위 누출을 점검하고, 판별력뿐 아니라 보정·업종/지역별 오류도 본다.
- 산출물: 문제 정의서, 재현 가능한 기준선/후보 실험, 검증표, 실패 사례, "서비스에 넣을지"에 대한 자신의 결론. 모델 성능이 낮아도 이유가 설명되면 분석 성과다.

### D-04 갱신과 Supabase 이행 검증

- 새 데이터가 들어왔을 때 행 수·키·상태·기준일·주요 지표가 어떻게 달라지는지 추적하고, 동권의 DB 이행 전후 결과를 독립 검증한다.
- 산출물: 자동 품질 점검 기준과 갱신 전후 비교 보고서. 임계값은 실제 변동을 본 뒤 정한다.

함께 살펴볼 질문 예: "영업 중인 점포의 생존 기간을 왜 폐업 점포와 똑같이 취급하면 안 될까?", "2024년에 예측한다면 2026년 데이터로 만든 상권 특징을 써도 될까?" 정답을 먼저 말하기보다 표본 5~10행으로 학생이 설명하게 돕는다.

## 김선경: 다중 데이터 분석·ML·에이전트 평가 트랙

김선경은 프롬프트만 맡지 않는다. **보조 데이터와 지역·시간 분석을 직접 수행하고**, 검증된 결과가 AI 상담에 실제 가치를 더하는지 평가한다.

### A-01 보조 데이터 결합과 독립 EDA

- `poi`, `area_context`, `legal_admin_map`, `station_traffic`, `parking`, `market`를 인허가 집계와 연결해 본다. 상가정보의 업종 체계, 법정동↔행정동, 역 이용량의 기간, 인구의 기준월, 주차장·시장의 공간 범위가 다름을 확인한다.
- 구·동별 업종 구성·다양성·인구·교통·개폐업 패턴을 비교하고, 조인 실패율과 결측 편향을 수치로 남긴다. 지도를 만들기 전에 좌표계·위치 정확도를 점검한다.
- 산출물: 결합 가능 데이터 목록, 지역/시점 기준표, 탐색 그래프와 해석의 한계. 세은의 데이터 사전과 서로 검토한다.

### A-02 한 가지 ML 질문을 학생이 선택

아래는 **선택지**이지 모두 구현할 체크리스트가 아니다. 데이터가 질문을 뒷받침하는지 확인한 후 한 가지를 깊게 수행한다.

- 지역별 월간 개업·폐업 건수의 다음 기간 예측: 최근 값/계절 평균을 기준선으로 두고 시계열·회귀·카운트 모형 후보를 비교한다. 시간 순서 검증, 지역별 오차, 사건이 적은 지역의 불안정성을 본다.
- 지역 유형 재탐색: 상가 구성·인구·교통 등으로 군집을 만들고 기존 규칙 기반 상권 유형과 비교한다. 전처리/척도 변화에 대한 군집 안정성, 설명 가능성, "좋은/나쁜 상권"이라는 과장 여부를 검토한다.
- 자리 재입점 패턴: 선경이 특히 관심 있다면 신규 인허가까지의 시간 문제를 정의한다. 세은의 자리·공실 정의 검증과 미래 관측 기간 확인이 선행되어야 한다.

산출물은 질문·데이터 가용성·기준선·후보·시간/지역 분리·오류 분석·해석을 포함한다. 모델이 기준선보다 낫지 않거나 데이터 결합 품질이 낮으면 왜 그런지 분석하고 다른 질문으로 전환한다.

### A-03 AI 상담에 데이터를 넣는 경로와 평가

- 참고 구현의 `core/tools.py`가 이미 답할 수 있는 질문(예: 주소별 자리 이력, 업종별 생존곡선, 지역 비교)과 새 분석이 필요한 질문을 구분한다. 모델 결과를 쓰려면 먼저 동권과 함께 **허용된 읽기 전용 도구**의 출력 형태를 정의한다: 질문에 맞는 집계/모델 버전, 기준일, 표본 수, 예측 범위, 불확실성, 결측·미지원 사유.
- 질문 사례를 지역 비교·자리 이력·생존/예측·보조 데이터·모호한 주소·답변 불가로 나눠 평가 세트를 만든다. 도구 선택의 적절성, 반환 수치와 최종 답변의 일치, 근거·한계 표시, 모르면 되묻기, 응답 시간을 기록한다.
- 산출물: 기존 `LLM + 도구`와 새 분석 도구가 실제로 어떤 질문에서 차이를 만드는지 보여 주는 평가표와 실패 사례. 근거가 없으면 도구 추가를 보류한다.

### A-04 데이터·모델 교차 검토

- 세은의 생존/결과 모델을 다른 지역·업종·기준일에서 재확인하고, 세은은 선경의 외부 데이터 조인·시간 분할을 검토한다. 결과가 다르면 어느 정의·표본·버전에서 갈라졌는지 기록한다.

함께 살펴볼 질문 예: "이 인구 수는 어느 달의 행정동 기준이고, 폐업 사건의 어느 시점과 결합해야 할까?", "모델을 추가해도 AI 답변의 정확성이 실제로 올라갔다는 증거는 무엇일까?" 선경에게 모델과 에이전트 중 하나만 맡기지 않는다.

## 협업 접점과 완료 판단

첫 주제는 병렬로 시작할 수 있다: 동권 E-01, 세은 D-01, 선경 A-01. 이후 데이터 사전·조인 기준을 공유한 뒤 세은 D-03과 선경 A-02가 진행되고, 검증된 결과만 동권 E-03으로 전달한다. 정확한 순서와 범위는 학생의 흥미·데이터 가용성·발표 일정에 따라 조정한다.

발표 자료에는 **기존 기술통계/규칙 기반 결과**, **새 통계·ML 실험의 질문과 기준선**, **검증 결과 및 실패 사례**, **서비스에 채택/보류한 근거**가 분리되어야 한다. 모델 점수 하나나 LLM 데모만으로 "데이터 분석을 완료했다"고 말하지 않는다.

방법 참고: [scikit-learn의 시계열 교차검증](https://scikit-learn.org/stable/modules/cross_validation.html), [확률 보정](https://scikit-learn.org/stable/modules/calibration.html), [lifelines의 Kaplan–Meier](https://lifelines.readthedocs.io/en/latest/fitters/univariate/KaplanMeierFitter.html)와 [Cox 모형](https://lifelines.readthedocs.io/en/latest/fitters/regression/CoxPHFitter.html). 라이브러리 설치나 모형 선택은 실험 질문이 정해진 뒤 결정한다.
