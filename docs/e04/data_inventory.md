## 3. 판단

**갱신이 꼭 필요한 것: 인허가(S1)와 그에 딸린 표 10개**
- 앱 화면의 대부분(자리 이력, 빈 자리, 공실률, 개·폐업, 사이클, 재입점 점수, 다음 업종)이 S1에서 나온다. 지금 기준일이 2주 지났다.
- 점수표 두 개(E-03·E-09)는 S1과 함께 다시 계산해야 한다. 그러지 않으면 새로 생긴 빈 자리에는 점수가 없고, 채워진 자리는 표에서 빠지기만 한다.
- 재학습은 하지 않고 고정 모델로 점수만 다시 낸다. 시점 변수(상가정보·인구·지하철)는 그때 가진 가장 최근 자료를 쓴다.

**주기를 늘려도 되는 것**
- 인구(S3): 월 1회 공개라 월 1회면 충분하다. A-07 예측표와 동네 맥락 인구를 같이 갱신한다.
- 상가정보(S2): 분기 단위로 갱신한다. `poi`·`legal_admin_map`·`area_context` 업종 구성·A-09를 같이 갱신한다. 법정동→행정동 대응표가 바뀌면 동네 카드 연결이 바뀌므로 점검 후 반영한다.
- 지하철(S4): 분기면 충분하다.
- 주차장·전통시장(S5·S6): 연 1회. 원천과 기준일부터 확정해야 한다(데이터 계약 7절의 남은 질문).

**API 자동화 가능성**

| 원천 | 판단 | 필요한 일 |
| --- | --- | --- |
| S1 인허가 | 가능, 지금은 키 문제로 막힘 | 공공데이터포털에서 42개 업종 API 활용신청(동권 님), 승인된 키를 로컬 `.env`에 저장. API 응답(영문 필드)을 지금 CSV 열 구성으로 바꾸는 변환. 대구 자치단체코드 9곳 × 업종별 페이지 수집(한 페이지 최대 100건, 일반음식점만 약 1,000회) |
| S2 상가정보 | 가능성 높음 | 활용신청과 시험 호출. 지금 CSV와 열 맞추기 |
| S3 인구 | 확인 필요 | API 제공 여부 확인. 없으면 웹 CSV를 월 1회 수동으로 받는다 |
| S4 지하철 | 확인 필요 | 파일변환 API 시험 |
| S5·S6 | 확인 필요 | 원천 확정 후 판단 |

**결론(제안)**
1. 지금 바로: S1을 **반자동**으로 시작한다. 주 1회 대구 전체 압축만 사람이 받고, 나머지(배치 → 점수 재계산 → 점검 → 전환 없는 DB 적재 → 요약)는 스크립트로 처리한다.
2. 이어서: S1 API 활용신청 후 받는 단계를 API로 바꾼다(완전 자동).
3. 월·분기 갱신(S3·S2·S4)은 같은 틀에 원천별로 붙인다. 점검(`check_data`)과 버전 적재 절차는 그대로 쓴다.
