# 날짜 범위·페이지·반복 수집 검증

2026-10-04 실행. `python scripts/check_restaurant_updates.py`로 공식 일반음식점 `/info`에 5회 요청했다. 결과: [update_probe.json](update_probe.json). 운영 데이터·스케줄은 변경하지 않았다.

## 범위와 결과

기존 Parquet에서 자치단체코드 3410000은 주로 중구에 대응했다. 주소상의 구와 발급기관 코드가 다른 소수 행도 있어 발급기관 코드와 현재 소재지를 같은 것으로 단정하지 않는다. 이번 대상은 **3410000 기관, 갱신시점 2026-10-03 00:00:00 이상 ~ 2026-10-04 00:00:00 미만**이다. 날짜는 API 문자열 그대로이며 API 시간대의 별도 보장은 확인하지 않았다.

| 검사 | 관찰 결과 |
| --- | --- |
| 첫 페이지 / 두 번째 페이지 | 5건 / 1건, 각 응답 totalCount=6 |
| 페이지 내부 및 페이지 간 키 중복 | 0건 |
| 수신 고유키 합계 | 6개, 해당 조건의 API 안내 건수와 일치 |
| 지역·날짜 조건 | 수신한 모든 행이 조건 만족 |
| 첫 페이지 반복 조회 | 키와 전체 행 해시 모두 일치 |
| 같은 키로 다시 병합 | 6개 → 6개. 임시 메모리 사전에서 확인, 실제 DB 저장 검증은 아님 |
| 끝을 22:17:50으로 제한(LT) | 0건 |
| 시작을 22:17:50으로 제한(GTE) | totalCount=6, 표본 5건에 해당 시각 포함 |

수신 6건의 갱신시점은 모두 `2026-10-03 22:17:50`이었다. 이는 6개 점포가 동시에 개·폐업했다는 뜻이 아니다. 배포 처리 시각일 가능성은 있지만 이 실험으로 원인을 확정하지 않았다.

## 판단과 한계

이번 작은 범위에서는 날짜 필터, 페이지 나눔, 반복 조회 후 키 기반 병합이 예상대로 동작했다. API 안내 건수에 대한 수신 일치는 확인했지만 원천 시스템의 누락 여부까지 검증한 것은 아니다. 정렬 고정 보장, 수집 중 자료가 바뀌는 경우, 삭제·과거 정정, 통신 실패 후 재시도는 별도 검증이 필요하다. 빈 결과의 지역/날짜 조건 검사는 확인할 행이 없는 것이므로 강한 검증 근거로 세지 않는다.

다음 실험은 이 6건을 기존 스냅샷의 `(org_code, mgmt_no, service)`와 비교해 새 인허가인지 기존 자료 수정인지 구분하는 것이다. 신규 인허가 날짜만으로 변경분을 수집하지 않으며, 검증 결과를 보기 전 자동 운영 갱신을 완료로 처리하지 않는다.
