# 추가·수정 반복 적용 실험

2026-10-04 실행. [검증 결과 JSON](upsert_simulation.json).

## 범위

기존 스냅샷의 기관코드 3410000·일반음식점 9,616행에서 상호·도로명주소·지번주소·인허가일·폐업일·폐업여부 6필드만 메모리에 복사했다. 앞서 검증한 갱신시점 2026-10-03 하루 범위를 API로 한 번 다시 조회해 6행 전체를 받았다. 원본 키 `(org_code, mgmt_no, service)`로 병합했다. 새 응답이므로 API 조회시각을 결과에 기록했다.

| 검사 | 결과 |
| --- | --- |
| 최초 적용 | 신규 2, 수정 4, 동일 0 |
| 행 수 | 9,616 → 9,618 |
| 동일 배치 재적용 | 신규 0, 수정 0, 동일 6; 9,618 유지 |
| 입력 6행 순서 반전 | 최초 적용 결과와 동일 |
| 마지막 행의 키 누락 주입 | 전체 배치 거부, 입력 상태 유지 |
| 배치에 중복 키 주입 | 전체 배치 거부, 입력 상태 유지 |
| 마지막 행에 폐업일 없는 폐업 주입 | 전체 배치 거부, 입력 상태 유지 |
| 원본 stores.parquet 해시 | 실행 전후 동일 |

잘못된 자료를 주입한 사례는 검증용 합성 오류이며 실제 API의 오류로 집계하지 않는다. 모든 행을 먼저 검증하고 복사본에만 적용하기 때문에 오류가 나도 입력은 수정되지 않는다. 반복 실행은 키 기준으로 중복을 만들지 않았다.

## 재현과 한계

```powershell
python scripts/compare_restaurant_updates.py --simulate
```

사용 환경은 앞선 실험의 pandas/pyarrow 환경과 동일하다. 병합 함수는 `scripts/simulate_upsert.py`에 있다. API 키는 제외 파일 `.env.data-go-kr`에서 읽는다. 비교 모드의 기존 결과는 덮어쓰지 않고 별도 simulation JSON을 작성한다.

이 실험은 **6필드 메모리 병합**이다. 원천 전체 스키마 수집, 디스크/DB 트랜잭션, 수집 완료 시각의 저장, 재시도, 삭제·지연 도착·순서가 뒤바뀐 서로 다른 버전 처리는 아직 검증하지 않았다. 신규 행의 전체 원천/파생 컬럼을 갖춘 운영 테이블을 만든 것이 아니다. 과거 갱신 배치를 나중에 적용하면 최신값을 덮어쓸 수 있으므로 원천 갱신시점 보존과 버전 비교가 다음 설계에 필요하다.

## 다음 단계
