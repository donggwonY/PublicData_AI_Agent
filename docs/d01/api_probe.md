# 일반음식점 API 첫 표본 조회

2026-10-04 사용자 활용신청 승인 후 실행. 공식 명세 출처: https://www.data.go.kr/data/15154916/openapi.do 의 내장 Swagger.

## 실행 결과

`python scripts/probe_restaurants.py` 실행 성공. HTTP 200, resultCode `0`, 첫 페이지 5행 수신. 결과는 [api_probe.json](api_probe.json)에 저장했다. 인증키는 Git 제외 파일 `.env.data-go-kr`에서 읽으며 URL 인코딩은 한 번만 적용한다. 출력과 결과 파일에는 키·요청 URL·원본 응답을 넣지 않는다.

요청: `/info`, `pageNo=1`, `numOfRows=5`, `returnType=JSON`, `cond[ROAD_NM_ADDR::LIKE]=대구광역시`. API가 돌려준 필터 대상 totalCount는 66,518이며, **도로명주소 필터 결과**다. 도로명주소가 없는 행이나 다른 주소 표기가 빠질 수 있어 대구 전체 또는 현재 영업점포 수로 사용하지 않는다. 처음 5행은 모두 영업/정상이며 대표 표본이 아니다.

핵심 필드 확인: `OPN_ATMY_GRP_CD`(자치단체), `MNG_NO`(관리번호), `LCPMT_YMD`(인허가일), `SALS_STTS_NM`(영업상태), `CLSBIZ_YMD`(폐업일), `DAT_UPDT_PNT`(갱신시점). 기존 stores의 `org_code`·`mgmt_no`에 업종을 더하는 키 구조와 대응할 후보가 확인됐다. 실제 개별 키 조인은 아직 실행하지 않았다.

표본 갱신시점은 `2026-10-03 22:17:50`. 명세 설명의 YYYYMMDDHHMMSS와 달리 구분자를 포함하므로 응답 파싱 시 둘 다 처리하고 원문도 보존해야 한다. 이 값은 실제 개업/폐업 발생시각이나 수집 완료 보장이 아니다.

## 상세 명세에서 새로 확인한 내용

- `/info` 설명은 매일 갱신하며 2일 전 기준으로 현행화한다고 명시한다. 이는 이번에 확인한 현행 명세의 설명이며 표본 응답만으로 실제 지연을 측정한 결과는 아니다.
- 한 페이지 최대 100건.
- `cond[DAT_UPDT_PNT::GTE]`, `cond[DAT_UPDT_PNT::LT]`로 갱신시점 범위를 지정할 수 있다. 자치단체 필터는 `cond[OPN_ATMY_GRP_CD::EQ]`다.
- `/history`는 기준일과 자치단체코드가 필수다. 기준일은 2026-01-01부터 조회일 전일까지라고 설명한다. 해당 조건 이름은 `cond[BASE_DATE::EQ]`인데 필드 설명에는 ‘미만’이라는 문구도 있어 경계 의미는 실험으로 확인해야 한다.

## 다음 검증

도로명 검색을 대구의 검증된 자치단체코드 목록으로 바꾸고 한 구·한 날짜 범위를 정해 2페이지 이상을 조회한다. 겹침 재수집의 키 중복 처리, 갱신시점 필터 경계, 과거 폐업·정정·삭제의 표현을 확인한다. 이번 실행은 인증과 표본 스키마 확인만 완료했으며 일일 자동 갱신·배포는 구현하지 않았다.
