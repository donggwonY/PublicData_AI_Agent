# 수집 실패·역순 도착 보호 실험

2026-10-04. **합성 데이터 기반 오프라인 실험**이며 실제 기관 장애나 운영 DB 트랜잭션 검증이 아니다. API 호출과 원본 Parquet 변경 없이 수행했다.

## 구현한 규칙

[staged_updates.py](../../scripts/staged_updates.py)는 기관·업종별 상태와 수집 구간, 페이지 조회 함수를 받아 새 상태를 반환한다. 입력 상태는 수정하지 않는다. 페이지 번호·전체 건수·행 수·키 중복·지역·날짜·행 필드를 모두 검증하고 나서만 새 데이터와 완료 경계시각을 함께 반환한다. 완료 경계는 조회 구간의 배타적 끝이며 실제 사업 사건 발생시각이 아니다.

키가 같은 기록은 원천 갱신시각을 비교한다. 더 최신이면 교체, 더 오래됐으면 건너뛰고, 시각과 값이 같으면 그대로 둔다. 시각이 같은데 내용이 다르면 명세상 순서를 결정할 수 없어 전체 구간을 보류한다. 원천 시각이 없는 기존 레코드와 비교하려 하면 보류한다. 이 규칙은 실험용 후보이고 원천 API의 버전·삭제 계약을 확정한 것이 아니다.

## 검증

```powershell
python -m unittest discover -s tests -p test_staged_updates.py -v
```

앱 제공 Python 3.12.14에서 **13개 통과, 종료 코드 0**.

완료 경계를 함께 반환하는 동작은 메모리 수준에서만 검증했다. 호출자가 디스크나 DB에 데이터와 경계를 따로 저장하면 중간 장애가 생길 수 있으므로, 운영 저장은 별도의 트랜잭션/버전 전환 검증이 필요하다. totalCount가 일정해도 동시 수정으로 페이지 내용이 바뀔 수 있다. 이 검사는 원천 누락 부재를 보장하지 않는다.

## 현재 실제 자료에 적용하기 전 필요한 것

기존 stores.parquet에는 원천 `DAT_UPDT_PNT`가 보존되어 있지 않다. 인허가일이나 빌드일로 이를 대신 채우면 수정 순서를 잘못 판단할 수 있으므로 운영 이행 전에 갱신시각을 포함한 초기 원천본이 필요하다. 지역·업종별 초기 수집 범위와 완료시각, 원천 날짜의 시간대, 삭제/정정 계약을 확인해야 한다.

다음 검증 대상은 API 이력 조회로 같은 기록의 과거 상태를 확인하고, 현재 조회의 변경시각과 어떤 관계인지 대조하는 것이다. 그 결과를 바탕으로 원천 전체본 수집 및 버전 저장 방식의 제안을 구체화한다. 자동 갱신 등록·운영 배포·DB 수정은 하지 않았다.
