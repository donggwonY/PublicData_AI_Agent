# 폐업 기록의 과거·현재 API 상태 대조

2026-10-04, 공식 일반음식점 `/history` 4회와 `/info` 1회 조회. [스크립트](../../scripts/probe_restaurant_history.py), [실제 응답 요약](history_probe.json).

대상은 `(3410000, 3410000-101-2026-00161, 일반음식점)` 한 건이다. 기존 스냅샷 해시를 확인하고 그 기록의 상호와 기관코드로 검색한 뒤 관리번호까지 일치하는 행만 비교했다. 각 요청의 검색 결과와 정확한 키 일치는 모두 1건이었다.

| 요청 기준일/조회 | 영업상태 | 폐업일 | 최종수정시점 | 데이터갱신시점 |
| --- | --- | --- | --- | --- |
| 이력 2026-09-23 | 영업/정상 | 없음 | 2026-05-04 14:50:33 | 2026-05-05 22:18:00 |
| 이력 2026-10-01 | 영업/정상 | 없음 | 2026-05-04 14:50:33 | 2026-05-05 22:18:00 |
| 이력 2026-10-02 | 폐업 | 2026-10-02 | 2026-10-02 10:57:41 | 2026-10-03 22:17:50 |
| 이력 2026-10-03 | 폐업 | 2026-10-02 | 2026-10-02 10:57:41 | 2026-10-03 22:17:50 |
| 현재 `/info` | 폐업 | 2026-10-02 | 2026-10-02 10:57:41 | 2026-10-03 22:17:50 |

## 확인한 내용

기존 Parquet의 9월 23일 closed=false와 같은 날짜의 이력 조회가 일치했다. 10월 1일에서 2일로 넘어가며 같은 키의 상태가 영업에서 폐업으로 달라졌다. 한 건의 실측이며 모든 업종·날짜 경계·지연 정정의 일반적인 동작을 증명한 것은 아니다.

## 분석에서 중요한 시간 구분

10월 2일을 요청했는데 10월 3일 갱신시각이 반환됐다. **사건일, 행정 수정시각, 공개 데이터 갱신시각, 우리 서비스의 수집시각**은 같지 않다. 이번 응답만으로 해당 기록을 10월 2일에 실제 조회할 수 있었다고 주장할 수 없다. 이력 API로 과거 데이터를 만든다고 당시 이용 가능했던 정보까지 자동 보장되는 것은 아니므로, 예측 실험은 수집 당시 스냅샷·수집시각을 보존하고 미래 정보 누출을 점검해야 한다.

응답 요약의 BASE_DATE는 null이었다(필드 부재와 null은 이 요약에서 구분하지 않음). 요청 기준일을 응답이 되돌려준 값으로 오해하지 않도록 요청 파라미터를 함께 기록했다. 상호 검색은 과거 상호가 달라졌을 때 기록을 놓칠 수 있으므로 검색 결과 없음은 삭제 증거가 아니다.

## 다음 단계

이력 조회 기능과 실제 폐업 전환 사례는 확인했다. 운영 자동 갱신을 위해서는 원천 갱신시각을 포함하는 초기본을 확보하고, 전체 수집·실패 복구·버전 저장·파생 테이블 재계산·앱 캐시 갱신을 연결해야 한다. 우선 한 기관·일반음식점 초기본 수집 계획을 작성하고 호출량·페이지 수를 확인한다. 현재 코드는 읽기 전용 검증이며 원본과 운영 데이터를 수정하지 않았다.
