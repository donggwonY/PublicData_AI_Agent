# 데이터 공개 주기와 자동 수집 조사

확인일: 2026-10-04. 공식 공공데이터포털의 상세 안내를 확인했다. 인증된 API 호출·파일 다운로드·운영 갱신은 수행하지 않았다. 페이지에 표시된 주기와 실제 사건 발생→공개 지연은 다르다.

## 옛 LOCALDATA 설명을 그대로 적용하면 안 되는 이유

[행정안전부의 2026년 통합 개방 안내](https://www.mois.go.kr/frt/bbs/type002/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000205&nttId=123477)는 공공데이터포털 통합과 인허가 과거 이력 조회 추가를 설명한다. 과거 LOCALDATA FAQ의 D-2·오전 8시 배포 설명을 새 API의 지연 보장으로 사용하지 않았다. `/history`의 존재만으로 완전한 증분 스트림이나 삭제 이벤트 제공을 주장하지 않는다.

## 첫 실험: 일반음식점 한 업종

목적은 “공개된 변경을 누락 없이 받아 같은 분석을 다시 만들 수 있는가?”를 확인하는 것이다. 아래는 제안이며 자동화 등록이나 운영 변경은 하지 않았다.

1. 공식 일반음식점 API 활용신청과 인증키 준비. GitHub PAT와 다른 키다. 키를 채팅에 붙여넣지 않고 로컬 비밀 설정에 보관한다.
2. 승인된 명세에서 자치단체 필터, 페이지 크기/끝 판정, 수정일·이력 날짜 필터, 응답 필드와 오류 코드를 확인한다. 매개변수 이름을 추정해서 구현하지 않는다.
3. 작은 표본을 조회해 원천 키(개방자치단체코드·관리번호·업종)와 기존 CSV 필드의 대응을 기록한다. 날짜/상태/취소 처리 및 과거 폐업 보존 여부를 확인한다.
4. 전체 초기본을 별도 저장한다. 신규 개업만 추가하면 기존 업소의 폐업·주소 정정을 놓치므로 기존 키의 수정도 반영한다. 증분 명세가 불충분하면 전체본 비교 방식을 먼저 평가한다.
5. 동일 구간 재수집 시 결과가 늘어나지 않는지, 페이지 일부 실패 시 성공 시점을 갱신하지 않는지, 정정/삭제가 다음 버전에 반영되는지 검증한다. 이력 조회 기간에 겹침을 주는 방식은 수정일 의미 확인 후 결정한다.
6. 새 데이터로 만든 별도 분석 버전에 D-01의 키·관계·기간·메타 검사를 적용한다. 통과 후에만 앱이 새 버전을 읽도록 한다. 실패하면 이전 버전을 유지한다.

제안 주기는 인허가 일 1회, 인구·교통 월별 새 버전 확인이다. 상가정보는 실시간 표기만으로 짧은 주기를 결정하지 않고 변경량·지연·할당량을 먼저 측정한다. 주차장·시장은 별도 기준일을 표시한다. 스케줄 실행 시각, 운영 도입 여부는 아직 결정하지 않았다.
