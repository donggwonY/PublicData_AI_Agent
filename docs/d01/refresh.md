## 현재 코드에서 확인한 답

새 데이터 반영 경로는 있지만 자동 실시간 반영은 구현되어 있지 않다. 원천 CSV 확보 → 배치 재계산 → Parquet → 앱 메모리 조회 방식이다. 원천 기관이 공개하기 전의 실제 개·폐업 사건을 이 앱이 알 수는 없으므로, 공개 주기·신고 지연·수집 간격·처리/반영 지연을 각각 구분해야 한다. 출처의 현재 공개 주기는 이번 조사에서 미확인이다.

| 단계 | 확인한 사실 | 자동 갱신에 필요한 확인/개선 후보 |
| --- | --- | --- |
| 수집 | `pipeline/build.py:load_raw`, `pipeline/external.py:read_external`은 로컬 CSV를 읽는다 | 공식 API/파일 제공 방식, 갱신 주기, 이용 조건, 수정·취소 데이터 제공 여부 확인 |
| 인허가 갱신 | `load_raw`는 org_code·mgmt_no·service에 대응하는 원본 키로 최종수정/갱신시점 정렬 후 중복을 제거한다 | 증분 입력이 실제로 누락 없이 제공되는지, 정정·삭제를 어떻게 반영할지 확인. 기준일은 사건 날짜 최댓값이므로 수집 완료 시각과 별도 관리 필요 |
| 실행 주기 | `run_batch.ps1`에 매일 03시 작업 스케줄러 등록 예시가 있다. 실행 대상은 인허가 배치뿐이다 | 스크립트 존재는 실제 스케줄 등록 증거가 아니다. 보조 배치·다운로드·재시도는 별도 검토 |

## 작은 다음 실험 후보

우선 원천 공개 주기를 확인하고 하루 한 번 갱신으로 충분한지 학생이 판단한다. 주기는 아직 결정하지 않았다. 운영과 분리된 복사본에서 새 버전 한 개를 만들고, 행 수·키·날짜 검사 통과 후 버전을 전환하며 실패 시 이전 버전이 유지되는지 검증할 수 있다. 운영 DB/배포 변경은 E-01·E-02 담당자와 결정할 사항이다.

현재 인허가 자료는 7개 업종, 보조 데이터는 서로 다른 기간의 단면이다. 인허가만 갱신했다고 인구·상가·교통까지 같은 시점의 실시간 데이터라고 표시하면 안 된다.
