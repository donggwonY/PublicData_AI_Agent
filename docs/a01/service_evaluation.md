# A-03 실제 서비스 첫 평가

2026-10-24 · 김선경 · 평가 실행 및 판정: Codex. 학생의 독립 채점은 아직 없음.

## 실행 조건

https://pubdai.streamlit.app/ 공개 앱에서 질문 3개를 같은 새 세션에 순서대로 입력했다. 질문 2는 질문 1의 후속이며 질문 3도 같은 대화 이력을 포함한다. 각 1회 실행으로 반복 성능 또는 일반 정확도를 추정하지 않는다. 정답 JSON·평가 기준은 모델에 제공하지 않았다. 따라서 이는 근거 문서 제공형 평가가 아니라 서비스 통합 평가다.

화면 표시: 데이터 db v3, 기준일 2026-10-13. 세 답변 모두 모델 gemini-3.5-flash. 공개 배포 커밋은 확인하지 않았으며 로컬 코드 606c179와 동일 배포라고 단정하지 않는다. 처음 휴면 상태였던 앱을 깨운 뒤 실행했다. 운영 코드·DB·배포 설정은 변경하지 않았다.

## 결과

| 질문 | 실제 답변 | 판정 | 이유 |
| --- | --- | --- | --- |
| 1. 출구 주변 300m/500m | 30개 / 56개가 영업 중이라고 답함 | 실패: 범위 대체 | 출구 합집합 42/72건 또는 중복 제거 41/70건이 아닌 단일 주소 중심 집계. 출구 기능 미지원 고지 없이 대체했고 현재 영업 표현도 부정확 |
| 2. 최근접 출구별 배정 | 출구 좌표가 없어 확인 불가라고 답함 | 기능 미지원; 한계 고지는 부분 충족 | 출구별 수를 만들지는 않음. 다만 “공공데이터에 포함되어 있지 않다”는 표현은 서비스 미연결과 공공데이터 자체 부재를 혼동. 공식 출구 자료는 A-01에 존재 |
| 3. 두 주소 비교·창업 유리 여부 | 39개 / 44개, 적다고 무조건 유리하지 않다고 답함 | 실패: 정의·근거 부족 | 같은 주소 포함/제외와 중복 제거를 구분하지 않음. 수요가 매우 많아 카페가 함께 유지될 수 있다고 단정하고 실제 후보 층을 묻지 않음 |

세 질문의 원래 필수 기준을 모두 충족한 답변은 없다. 미지원과 오답을 구분하며 이를 서비스 전체 정확도 0%라고 해석하지 않는다.

## 항목별 판정

- 질문 1: 반경별 정답 수치 실패, 출구 합집합·중복 방지 설명 실패. 자료 시점과 직선거리 설명은 충족했으나 현재 영업 확인과 기록 수 구분은 실패.
- 질문 2: 최근접 배정 수치와 순위는 미지원. 출구별 반경 집계와 최근접 배정 구별도 검증할 답변이 없음. 고객 유입·유의성 단정은 하지 않았으나 앞선 30개를 계속 사용하고 자료 부재 범위를 과도하게 일반화함.
- 질문 3: 총수·같은 주소 수·제외 수 구분 실패. 주소 중심임은 설명했으나 기준 카페 좌표와 서비스 자리 좌표 차이를 고지하지 않음. 같은 주소 경쟁 제외 설명 없음. “적으면 유리” 단정은 피했지만 측정하지 않은 수요를 확정적으로 설명함. 실제 후보 주소·층 요청 없음. 자리 이력을 조회한 척하지는 않았음.

## 숫자 차이 원인 확인

로컬 서비스 find_nearby를 APP_DATA_SOURCE=parquet로 별도 실행했다. 이는 공개 앱 도구 원문을 직접 추출한 것이 아니라 로컬 재현이며, 모델 답변 생성 시험과 구분한다. 결과는 [service_tool_probe.json](service_tool_probe.json).

- 동대구역 입력: 동대구로 550의 단일 자리 좌표로 선택, 300m 30건·500m 56건. 공개 답변 수치가 로컬 도구 결과로 재현되므로 숫자 자체를 임의 생성했다고 단정하지 않는다. 문제는 출구 합집합 질문을 다른 범위로 바꾼 것이다.
- 실제 질문 3 도구 인자는 대구 동구 동부로22길 9 및 대구 동구 동부로 149였다. 같은 인자로 로컬에서도 39·44건 재현. 인허가 자리 좌표 중심, 업종 부분문자열 검색, 동일행 미제거다. 기존 근거 38·43건은 카페 좌표 중심·정확 카페 분류·동일행 제거 기준이므로 단순 차감만으로 AI 산술 오류라 하지 않는다.
- 서비스의 부분문자열 검색은 스터디 카페를 포함할 수 있다. 원래 평가의 cat_s == 카페와 다르다.
- 추가 입력 민감도: 동부로22길 9처럼 구 이름 없이 넣으면 주소 토큰 포함 검색 52후보 중 동부로22길 91-11 1층을 자동 선택했고 25건이 나왔다. 실제 공개 질문 3은 모델이 구를 붙여 올바른 9번지로 조회했으므로 이 주소 오선택을 이번 공개 답변의 원인으로 섞지 않는다. 별도 재현된 입력 위험이다.

## 우선 수정 제안

1. 서비스가 출구 분석을 지원하지 않으면 단일 주소 수치를 출구 답변으로 대체하지 말고, 미지원과 집계 기준을 명시한다.
2. 주소의 건물번호가 정확히 맞는지 검사하고 후보가 모호하면 자동 첫 선택 대신 확인한다. 구 유무에 따라 9가 91-11로 바뀌는 재현 사례를 회귀 검사로 삼는다.
3. 정확 카페 분류·중복 처리·동일 주소 제외·중심 좌표를 도구 계약에 명시한 뒤 평가 근거와 맞춘다.
4. 실제 수요·임대료·영업 상태를 확인하지 않았다면 추정 또는 미확인이라고 표현한다.

수정 구현과 공개 배포는 이번 평가에 포함하지 않았다. 다음은 팀과 우선 수정 항목을 공유하고 같은 질문으로 재평가하는 것이다.

## 2026-10-24 로컬 수정 및 도구 재평가

첫 평가 뒤 사용자 요청으로 서비스 코드를 수정했다. 공개 앱 평가 원문은 수정 전 증거로 보존한다.

- 주소 토큰 검색의 건물번호를 숫자 경계로 검사하여 9가 91-11에 매칭되지 않도록 했다.
- 여러 건물 후보를 자동 첫 선택하지 않고 전체 주소·층 확인을 요구한다. 같은 건물의 층 미지정은 기존 대표 자리 선택을 유지하므로 반환 center와 중심 정의를 확인해야 한다.
- 역 이름/출구를 find_nearby에 넣으면 기능 미지원 오류를 반환한다. 출구별 분석 자체를 새로 구현한 것은 아니다.
- 카페 조회는 cat_s 정확 일치를 사용하고 원기록·동일행 제거·같은 도로명 건물주소 제외 수와 기준을 함께 반환한다. 다른 업종은 기존 검색어 방식 유지. 인허가 생존분석의 카페 정의는 변경하지 않았다.
- 시스템 프롬프트와 도구 설명에 미지원 범위, 현재 영업 단정 금지, 미확인 수요 설명 제한을 추가했다.

도구 재평가: 동부로22길 9는 짧은/전체 주소가 같은 중심으로 연결되고 원기록 39·동일행 제거 38·같은 주소 1·제외 37건. 동부로 149는 후보가 모호하면 확인을 요청하고, 지하1층으로 명시하면 동일행 제거 43·같은 주소 11·제외 32건이다. 이는 선택한 인허가 자리 좌표 중심 결과이며 모든 반경에서 A-01 카페 좌표 중심과 같다는 보장은 아니다.

검증: `python -m unittest tests.test_core_units tests.test_a03_regressions` 17개 통과. `python -m tests.smoke_test` ALL PASSED 0(의도한 오류 경로 포함). 스모크의 정상 주소 사례는 모호성을 없애기 위해 동성로5길 83 1층으로 명시했고, 별도 회귀 검사는 모호한 주소 거부를 검증한다.

로컬 모델 API 키가 없고 공개 앱은 deploy 브랜치이므로 수정 후 실제 Gemini 재평가는 미수행이다. 프롬프트 수정 효과를 검증 완료라고 주장하지 않는다. DB·공개 배포·GitHub 푸시는 하지 않았다. 다음은 변경 검토·main 공유 후 염동권의 배포 절차를 거쳐 같은 세 질문으로 재평가하는 것이다.
