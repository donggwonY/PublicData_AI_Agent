# 멘티 협업 및 Git 작업 흐름

## 담당 초점

| 멘티 | 우선 담당 | 검토 가능한 산출물 |
| --- | --- | --- |
| 염동권 | 화면·서버·저장소 계약·분석 결과 통합·배포 | 재현 가능한 실행/배포 절차, 데이터/모델 조회 인터페이스, 검증·장애 대응 |
| 김세은 | 데이터 품질·정의·탐색 분석·생존/결과 모델 | 데이터 사전·품질표, 코호트/중도절단 분석, 기준선과 예측 검증 |
| 김선경 | 보조 데이터 결합·지역/시간 ML·AI 도구 평가 | 결합/EDA 기록, 선택한 ML 질문의 실험, 도구·답변 평가표 |

각자 자기 담당 밖의 코드도 수정할 수 있습니다. 다만 지표 정의 변경은 김세은, AI 답변 기준 변경은 김선경, 배포 설정 변경은 염동권과 함께 확인합니다. 발표 범위와 중요한 설계 결정은 관리자가 조율합니다.

에이전트는 [멘티 플레이북](MENTEE_PLAYBOOK.md)의 확인 항목과 완료 기준을 활용하고, [작업판](WORKBOARD.md)의 실제 증거를 보고 다음 일을 제안합니다. 세은과 선경은 모두 에이전트의 도움으로 데이터 분석·ML에 참여합니다. 에이전트가 기술적 추천안·구현·검증을 적극 제공하고, 학생이 전문적인 판단이나 이해 확인에 답해야만 작업을 진행하는 방식은 피합니다. 에이전트의 제안과 학생이 직접 표현한 의견은 구분해 기록합니다. 선경을 프롬프트 작성만 하는 역할로 축소하지 않습니다.

## 작업 단위

1. 개발 세션을 시작하면 Codex의 `$pull` 또는 Claude Code의 `/pull`을 실행합니다. 에이전트가 원격 `main`을 가져와 fast-forward가 가능할 때만 반영합니다. 작업 파일이 수정돼 있거나 이력이 갈라졌다면 덮어쓰지 않고 해결 방향을 안내합니다.
2. 이슈 또는 작업 메모에 목적, 완료 조건, 담당, 관련 데이터 기준일을 적습니다.
3. 각 멘티는 기본적으로 `main`에서 작업합니다. 작업을 공유할 때 Codex의 `$commit-push` 또는 Claude Code의 `/commit-push`를 실행합니다.
4. 에이전트가 변경 내용과 필요한 검증을 확인하고 커밋한 다음 원격 `main`을 다시 가져옵니다. 다른 멘티의 커밋이 앞서 있으면 fast-forward하거나 자신의 커밋을 최신 이력 위에 rebase합니다.
5. 충돌이 나면 에이전트가 양쪽 변경을 읽고 통합해 다시 검증합니다. 이후 `main`에 강제 푸시 없이 반영하고 커밋·검증 결과를 알려줍니다. 판단이 어려운 충돌이나 권한 오류만 사람에게 전달합니다.

### 에이전트의 작업 전 확인

1. 최신 지침을 pull하고 학생 프로필·작업 문서를 확인합니다. 로컬 프로필이 없으면 `$mentee-init` 또는 `/mentee-init`을 안내하되, 이미 요청된 작업을 대신 다른 학생 이름으로 기록하지 않습니다.
2. 사용하려는 프로그램이 읽는 연결 설정을 확인합니다. `pipeline.load_supabase`와 앱의 DB 읽기 경로는 `APP_DATABASE_URL`을 사용합니다. 적재 스크립트에서는 **프로세스 환경변수 > `--env-file`의 `.env`** 순서이므로 오래된 환경변수도 점검합니다. `.env.example`은 빈 항목과 설정 목적을 안내하며 실제 비밀값은 제공하지 않습니다.
3. 접속 문자열에서 프로젝트 ID·호스트·계정 종류를 확인하고 실제 연결 후 현재 사용자·대상 스키마·현재 버전을 읽기 전용으로 확인합니다. pooler 사용자명은 `<role>.uoiamnbkzlvlskngataq`, direct 호스트는 `db.uoiamnbkzlvlskngataq.supabase.co`여야 합니다. 사용자명에 프로젝트 ID가 없는 설정은 이 프로젝트에서 받은 접속 정보인지 별도 확인합니다. 비밀번호·전체 URL·Secrets 본문은 출력하지 않습니다.
4. 조회에는 읽기 전용 계정, 적재에는 해당 스키마에 쓰기가 허용된 계정을 사용합니다. `app_reader`는 조회만 가능합니다. 다른 학생의 PC에 비밀값이 자동 배포되는 것은 아니므로, 설정이 없으면 관리자가 해당 학생에게 필요한 최소 권한의 연결을 별도로 제공해야 합니다. 에이전트는 권한을 임의로 넓히지 않습니다.
5. 대상이 다르거나 권한이 부족하면 DB 단계만 중단하고 로컬 설정에 필요한 항목을 알려줍니다. 독립적인 로컬 분석·문서화는 진행할 수 있습니다. 기존 `.env`의 Git 토큰 등 다른 설정은 보존합니다. 이전 과정에서 사용한 `SOURCE_DB_PASSWORD`·`TARGET_DB_PASSWORD`·`TARGET_APP_READER_DATABASE_URL`은 적재 스크립트가 자동으로 읽는 키가 아닙니다.

### 학생별 작업과 저장

- **김세은**: 새 공유 DB의 자료·버전을 기준으로 품질·코호트·갱신 검증을 수행하고, 공유할 분석 결과를 같은 프로젝트의 분석용 스키마·표에 저장합니다.
- **김선경**: 같은 DB·입력 버전으로 보조 데이터 결합·ML 실험·도구 평가를 수행하고, 공유할 실험 결과도 같은 프로젝트에 저장합니다.
- **염동권**: 새 DB의 스키마·조회·적재·권한과 운영 앱 연결을 관리하고, 두 학생의 검증된 결과를 운영 흐름에 반영합니다.

이 구분은 담당 초점이며 다른 영역의 참여를 막지 않습니다. 분석용 스키마·표·쓰기 계정은 작업 목적에 맞게 정하고 기록합니다. 아직 생성·권한 설정하지 않은 분석용 저장소를 사용 가능한 것으로 가정하지 않습니다. 실험 결과를 서비스용 `app` 표에 덮어쓰거나 운영 데이터 전체를 지우지 않습니다. DB 적재 후 프로젝트·스키마·표·행 수·입력/결과 버전과 재조회 검증을 작업 문서에 남겨야 "새 공유 DB에 저장 완료"로 기록합니다.

운영 갱신의 `--fresh`는 `app` 스키마 전체를 삭제하는 옵션이고 `--activate`는 서비스 버전을 바꿉니다. 염동권과 조율한 운영 반영 요청 범위에서만 아래 절차를 수행하며, 백업·행 수·주요 조회 일치·되돌리기 경로를 확인합니다. 새 대상은 Pro이므로 과거 무료 한도 때문에 `--fresh`가 항상 필요하다고 가정하지 않습니다.

## 서비스 코드와 배포 브랜치

서비스 코드는 `service/`에 있습니다(2026-10-11 이전). `main`은 모두가 푸시하는 작업 브랜치이고, 공개 앱은 **`deploy` 브랜치**만 읽습니다. `main`에 푸시해도 공개 앱은 바뀌지 않습니다.

- `service/` 아래 코드나 `service/data/processed`를 바꾸는 사람은 `service/` 안에서 Python 3.12 가상환경으로 `python -m unittest tests.test_core_units`와 `python -m tests.smoke_test`를 통과시킨 뒤 `main`에 올립니다. 배포 설정·`service/requirements.txt` 변경은 염동권과 함께 확인합니다.
- 배포는 염동권이 맡습니다. 순서: ① 최신 `main`에서 위 테스트 통과 확인 → ② `main`의 해당 커밋을 `deploy`로 fast-forward 푸시(강제 푸시 없음) → ③ Streamlit Cloud에서 Reboot → ④ 배포 로그의 패키지 버전과 공개 화면의 기준일·대표 수치 확인 → ⑤ 작업판에 배포한 커밋과 확인 결과 기록.
- 데이터를 갱신할 때(염동권): ① `service/data/raw`의 원본으로 `python -m pipeline.build` → ② 테스트 통과 후 `main`에 올림 → ③ 위 공유 DB 대상·쓰기 계정·백업·용량을 확인하고 `python -m pipeline.load_supabase --processed data/processed --env-file ../.env --activate` → ④ 공개 앱 Reboot 후 사이드바의 "데이터 db v<번호>"·기준일 확인. 전체 교체가 요청된 경우에만 `--fresh --start-version <다음 번호>`를 추가합니다. 기본 용량 상한은 450MB이므로 기존 버전과의 합계가 넘으면 보존·교체 방식을 먼저 정하고 재실행합니다. 코드 변경이 함께 있으면 위 배포 순서를 따릅니다. 공개 앱의 Secrets에는 읽기 전용 `app_reader` 접속 정보만 둡니다.
- 문제가 생기면 `deploy`를 고치지 말고 `main`에서 수정해 다시 올립니다. 급히 되돌려야 하면 이전에 배포한 커밋을 가리키는 되돌림 커밋을 `main`에 만들고 같은 순서로 올립니다.
- 다른 멘티와 그 에이전트는 `deploy`에 푸시하지 않습니다.
- 공개 앱의 Streamlit Cloud 메뉴에서 **Codespaces 기능을 쓰지 않습니다.** Streamlit이 배포 브랜치(`deploy`)에 `.devcontainer/devcontainer.json`을 자동으로 커밋하고, Codespaces 안의 커밋은 `main`을 거치지 않고 공개 앱을 바로 바꿉니다. 그러면 `deploy`가 `main`과 갈라져 fast-forward 배포가 막힙니다(2026-10-17 `ee1b3a2` 사례, 2026-10-29 정리).

## 코딩 에이전트와 Git 게시

`pull` 스킬은 `scripts/pull_main.py`로 개발 시작 전 원격 `main`을 확인합니다. `commit-push` 스킬은 학생 대신 `scripts/commit_push.py`의 커밋·동기화·푸시 단계를 실행합니다. 동기화 후와 충돌 해결 후에는 관련 검증을 다시 합니다. 푸시 직전에 원격이 바뀌면 다시 동기화하며, 실패가 반복되면 현 상태를 보존하고 원인을 설명합니다. 일상 작업에는 PR을 사용하지 않습니다.

GitHub 토큰은 개인별 fine-grained PAT로, 이 저장소의 `Contents: Read and write`만 부여합니다. 초기 설정 스킬이 질문과 로컬 저장을 처리하며, 토큰을 명령줄 인자·원격 URL·커밋에 넣지 않습니다. `.env`와 `.mentee/profile.json`은 로컬 전용이며 Git에서 제외됩니다. 설정 스크립트는 pre-push 훅을 활성화해 비밀 파일과 토큰 형태 문자열이 포함된 커밋의 푸시를 거부합니다. `.env`를 분실하거나 노출하면 GitHub에서 토큰을 폐기하고 새로 만듭니다.

## 관리자 체크포인트

분석 정의·데이터 출처 변경, 모델·할당량 변경, 공개 배포와 비용 발생, 사용자 데이터 저장 정책은 관리자가 이해할 수 있도록 문서와 테스트 결과를 남깁니다. 설계가 바뀌면 `docs/IMPLEMENTATION_DESIGN.md`를 함께 수정합니다. 이런 결정을 멘티가 단독으로 확정하기 어렵다면 게시 전에 관리자와 논의합니다.

## 코딩 에이전트 지침 관리

공통 지침은 `AGENTS.md`만 수정합니다. `CLAUDE.md`의 `@AGENTS.md`가 동일한 내용을 Claude Code에 전달합니다. 프로젝트 스킬은 `.agents/skills/<이름>/SKILL.md` 한 곳에 작성하고 `python3 scripts/link_skills.py`로 `.codex/skills/<이름>`과 `.claude/skills/<이름>` 링크를 생성합니다. 스킬 이름·설명은 두 도구에서 이해할 수 있는 공통 YAML 필드만 사용하고, 실행 명령은 둘 다 사용할 수 있는 로컬 스크립트를 가리키게 합니다. 새 스킬을 추가하면 두 경로가 같은 원본을 가리키는지 확인합니다.
