## 1. 방향 (E-03 재입점 점수와 같은 방식)

- 앱에는 모델을 넣지 않는다. 로컬 배치가 현재 빈 자리의 확률을 계산해 점수표로 저장하고, 앱은 읽기만 한다.
- 대상은 E-03 재입점 점수와 **같은 후보**다.
  - 앱의 "인허가 공백 후보"(공백 90일~3년, 단일 점포 자리) 4,536곳
  - 기준일 2026-11-06
- 확률의 뜻: "앞으로 2년 안에 점포형 가게가 들어온다면 그 업종 묶음일 확률"(7가지). 들어올지는 같은 자리의 E-03 점수가 답한다.

## 3. 저장 설계 (요청 시)

| 단계 | 내용 | 비고 |
| --- | --- | --- |
| 분석용 보관 | `analysis.e09_next_tenant_scores`, 기본키 (`batch_id`, `uid`), 관리자만 접근 | E-03 `analysis.e03_vacancy_scores`와 같은 권한·재실행 안전 규칙(같은 batch_id가 다른 내용이면 중단). 1년 뒤 검증 기준본 |
| 운영 표 | `app` 스키마 새 버전에 `next_tenant_scores` 추가(앱 읽기 전용) | `current_version` 전환은 기존 적재·검증 절차로 요청 시 |

열 구성:
- `uid`, `occupant_id`, `vacant_days`, `prev_group`, `prev_group7`
- `p_<묶음>` ×7: 모델 확률
- `typical_<묶음>` ×7: 이동표 비교선
- `top1~3`, `top1~3_p`
- `data_reference_date`, `generated`, `model_version`(= batch_id)

앱은 자리 상태(공백 일수·기준일)가 점수와 같을 때만 읽는다(E-03 `vacancy_outlook`과 같은 일관성 검사).

## 4. 화면·AI 상담 연결 (안 A, 요청 시)

- **자리 이력 화면**: 재입점 카드(E-03) 바로 아래에 "다음 가게가 들어온다면, 어떤 업종일까" 블록을 둔다.
  - 상위 3개 막대와 확률(정수 %)
  - 막대 위 이동표 비교선(직전 업종 자리 뒤에 보통 들어온 비율)
  - 나머지 묶음은 합계로 표시
- **한 줄 해석**: 1순위 묶음이 이동표보다 일정 수준 이상 높거나 낮을 때만 "높은 편/낮은 편"이라고 쓴다. 문턱은 구현 때 정한다. 1순위 단정("○○가 들어올 거예요")은 쓰지 않는다.
- **주변 상황(참고)**: 반경 약 300m 묶음 비중과 최근 1년 개업 비중을 사실 문장으로만 쓴다. 원인 표현은 금지한다.
- **정의·근거·한계 접기**: 조건부 확률, 2차 평가 수치(로그 손실 1.32 vs 1.42, 상위 3개 85.7% vs 83.2%), 평가 구간이 1차와 겹친다는 점, 자유업 미반영, 7묶음.
- **AI 상담 도구**: 자리 조회 도구 결과에 `next_tenant` 필드를 추가한다.
  - `display` 문장 + `basis` + `caveat`(기존 도구 형식)
  - 답변 규칙: "들어온다면" 조건을 빠뜨리지 않는다. E-03 재입점 확률과 곱해 말하지 않는다(결합 확률은 따로 검증하지 않았다).
- 화면과 AI 상담은 같은 문장 함수를 공유한다(기존 원칙).
